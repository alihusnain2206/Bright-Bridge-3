## ⚠️ CRITICAL ORDERING RULE

Do NOT activate any second location for any company until the employee JWT fix (Part C)
is built and verified. If a second location goes active first, shifts will silently land
under the wrong location's UUID and be permanently mis-attributed, and the sync will drop
them. The test sequence at the end respects this order — follow it exactly.

## PART A — Schema additions

1. `locations.is_primary` (boolean, default false). Backfill: for every company, set
   is_primary=true on its original location (the one seeded in Phase 1 — the single
   currently-active row per company). Exactly one primary per company; enforce in the
   create/edit endpoints (a location cannot be deactivated while is_primary=true;
   reassigning primary is out of scope this phase — just protect it).
2. `locations.latitude` + `locations.longitude` (numeric, nullable). Per EasyTeam's docs,
   Location objects passed to the SDK REQUIRE latitude and longitude. Backfill the two
   seeded locations (LOC-SUNSHINE, LOC-RAINBOW) from the in-memory store's coordinates.
   Add Latitude/Longitude fields to the Add/Edit Location form (plain numeric inputs,
   with helper text: "Find these on Google Maps — right-click the building → copy
   coordinates"). Required on CREATE of new locations; existing rows may stay null until
   edited, but any location being ACTIVATED (is_active → true) must have coordinates —
   block activation with a clear message if missing.

## PART B — resolveCompanyLocationId determinism

Update lib/location.ts: when reading from the locations table, select the is_primary=true
row (fallback: ORDER BY created_at ASC LIMIT 1 if none marked). This removes the
non-deterministic first-active-row behavior once multiple locations are active. The
in-memory store short-circuit for seeded companies can remain (their store value IS their
primary), but confirm the DB path is deterministic.

## PART C — Employee JWT uses the employee's own location

In auth.ts token-by-role (~line 476), the employee branch currently falls back:
user.locationId ?? resolveCompanyLocationId(companyId). Change the resolution to:

1. user_accounts.locationId if set
2. else resolveEmployeeLocationId(employeeId) — the employee's assigned location's
   easyteamLocationId (helper built in Phase 1)
3. else resolveCompanyLocationId(companyId) (existing behavior, now the last resort)

Apply the same resolution to the manager branch (managers are employees too — their
personal clock-in should use their own location; their MANAGEMENT scope comes from
user_accounts.locationId which step 1 already covers).

Also: backfill user_accounts.location_id from the linked employee's employees.location_id
for all existing accounts (boot migration, idempotent, log each). Your audit found all 16
ORG-SUNSHINE accounts have it NULL. And ensure the auto-account-creation path (wizard)
sets user_accounts.locationId from the employee's location at creation time going forward.

## PART D — Hours sync iterates ALL active locations per company

easyteam.ts sync (~line 519): today it builds one {companyId, locationId} entry per
company. Change to: for each company, query ALL is_active=true locations and call
fetchEasyTeamShiftsForLocation once per location, unioning results into the same
minutesByEmp / shift-persist flow. The existing foreign-location guard
(s.locationId !== etLocId) stays — it now correctly scopes each per-location batch.
Ensure no double-counting if EasyTeam returns the same shift in two fetches (dedupe by
shift id before persisting). skippedForeignShifts should now only count genuinely
foreign (other-company) shifts.

## PART E — SDK launcher: per-location employee maps

useEasyTeamLauncher.ts (~line 80): stop spreading all employees into every location.
Build each location's `employees` map from actual assignment: employee.id included in a
location's map only when employees.locationId matches that location. Per EasyTeam docs,
each Location object passed must include: id (easyteamLocationId), latitude, longitude,
name, timezone (when known), employees map. The endpoints feeding the launcher
(GET /api/easyteam/employees or equivalent) must return each employee's locationId so
the frontend can build the maps — add it to the response if absent.

Also update the pages that pass ALL_STATIC_LOCATIONS (dashboard-manager.tsx etc.) to
instead fetch the company's active locations from GET /api/locations and build the
per-location maps. Employees assigned to exactly one location should see NO location
picker at clock-in; the picker appears only if an employee appears in 2+ location maps
(not applicable yet — our model is single-location per employee — but the data shape now
follows the docs contract so it works when that changes).
