STEP 2 — BUILD
A. New locations table

Columns: id, companyId, code (text — client convention like "100", "200"), name, address1, address2, city, state, zipcode, easyteamLocationId, rollfiLocationId, isActive, createdAt. Follow existing schema conventions (snake_case, Drizzle, same file structure as other tables).

B. New departments table

Migrate the in-memory department model as-is: id, companyId, name, type (standard|daycare|custom), isDefault, isActive, createdAt. Seed with the same standard + daycare defaults currently seeded in memory.

C. Seed one location per existing company

Boot migration (idempotent, same pattern as bootBackfillRollfiUserIds): for every company, create one location from its existing data — name from locationName or company name, address fields from the company row, easyteamLocationId from the current resolved EasyTeam location, rollfiLocationId from companies.rollfiLocationId. Code defaults to "100". Log each created location. No-op on subsequent boots.

D. employees.locationId

New nullable FK column to locations.id. Boot migration: assign every existing employee to their company's (single) location. Keep the old workLocation text column untouched for now (removal is a later cleanup) — but nothing should write to it going forward; new employee creation writes locationId (the company's single location, since no picker exists yet).

E. Store/read migration
Departments: all reads/writes that currently hit the in-memory department array must go to the DB table. Department CRUD endpoints (Settings → Departments tab) now persist. The in-memory array becomes dead code — remove it or leave clearly commented as removed.
Locations: reads that currently hit the in-memory Location store must read from the table. resolveCompanyLocationId keeps its exact signature and fallback chain (store → DB companies.rollfiLocationId → LOC-{companyId} derived) but now consults the locations table first. Additionally create (but do not yet use anywhere new) a helper resolveEmployeeLocationId(employeeId) that returns the employee's location — this is the function later phases will use.
EasyTeam JWT building, employee registration, and shift sync must resolve to exactly the same location IDs as before — this is the highest-risk area (the schedule-grid bug lived here). Do not change what IDs get passed; only change where they're read from.
