THE PROBLEM

Your recent audit found a cluster of endpoints in easyteam.ts protected by requireAuth only — no role check, and assertCompanyAccess absent:

GET /easyteam/employees

GET /easyteam/timesheets
POST /easyteam/token

Two distinct gaps per endpoint: (a) no role authorization, (b) no verified company scoping.

"No assertCompanyAccess call" does not automatically mean data is exposed — the data may be scoped some other way. Confirm what is actually reachable before changing anything:

For each endpoint above, report how companyId is currently obtained (from the session? a query param the caller controls? a body field?).

Report findings before proceeding to Step 2.

STEP 2 — FIX (after findings reviewed)

For each endpoint, apply BOTH dimensions:

Role authorization — appropriate to the action, following the role guard patterns already used elsewhere in the codebase (requireRole / inline role arrays — match the existing convention, don't invent a new one):

Timesheet approval and any write/mutation → super_admin, owner, manager only
Company-wide employee/member/hours/timesheet reads → super_admin, owner, manager
Token issuance and status → must remain reachable by employees (they need it for the time clock), but still company-scoped
Propose the specific role set per endpoint in your report and flag any you're unsure about rather than guessing

Company scoping — use the same assertCompanyAccess pattern applied in the earlier hardening pass on clients.ts / people.ts / rollfi.ts. A caller must never receive or affect data for a company they don't belong to, regardless of what companyId they pass. Derive company from the session where possible rather than trusting caller-supplied values.
