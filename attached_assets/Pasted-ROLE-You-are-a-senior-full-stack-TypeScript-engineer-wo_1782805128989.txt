ARCHITECTURAL CONTEXT — WHY THIS 
MATTERS:

This platform sits between two 
systems with opposite state models:

ROLLFI is a system of record. It 
permanently persists employee status 
on its own servers. Changing an 
employee's status there REQUIRES an 
explicit, authenticated API call 
(deactivateUser / terminateUser / 
reactivateUser). Once called, Rollfi 
remembers that state indefinitely 
until told otherwise.

EASYTEAM is stateless from our 
integration's perspective. It holds 
no persistent employee roster of its 
own for our embedded use case — every 
time the Time Clock iframe initializes, 
our backend constructs and signs a 
fresh JWT containing the CURRENT 
employees array. EasyTeam has no 
concept of "remove this employee" — 
it simply renders whoever is present 
in the most recently issued token. 
Therefore, EasyTeam access control is 
achieved entirely by what we choose 
to include in that array at JWT 
generation time, not by any EasyTeam-
side API call.

This means: BrightBridge's local 
employee.status field is the single 
source of truth that drives EasyTeam 
visibility. Rollfi requires an active, 
explicit sync call. EasyTeam requires 
nothing but a correct filter.

PART 2 — STORE LAYER

Add a single method to the store 
(store.ts) responsible for status 
transitions:

updateEmployeeStatus(
  employeeId: string,
  newStatus: EmployeeStatus,
  meta?: Partial<Employee>
): Employee | null

This method must:
- Locate the employee by employeeId
- Validate the transition is legal 
  (see state machine rules below)
- Apply newStatus and any meta fields
- Persist to the existing data store
- Return the updated employee record, 
  or null if not found

STATE MACHINE RULES (enforce these 
server-side, not just in the UI):

active → on_leave: allowed
active → terminated: allowed
on_leave → active (reactivate): allowed
on_leave → terminated: allowed
terminated → anything: NOT ALLOWED, 
  terminal state

If an illegal transition is attempted, 
the store method (or the calling 
route) must reject it with a clear 
error rather than silently applying it.

PART 3 — BACKEND ROUTES (rollfi.ts)

Add three new authenticated routes. 
Follow the exact existing patterns 
already used in this file for 
headers, logging, and error shape 
(rollfiHeaders(), req.log.info/error, 
assertNoRollfiError where applicable).

ROUTE 1: POST /rollfi/employees/deactivate
Body: { employeeId: string, 
        reason?: string, 
        expectedReturnDate?: string }

Logic:
1. Require req.session.userId, else 401
2. Resolve employee via store; 404 if 
   missing
3. Reject if employee.status === 
   'terminated' (400, explicit message)
4. Resolve rollfiUserId via 
   store.getRollfiEmployee(employeeId); 
   400 if not onboarded to Rollfi
5. Call Rollfi: method 
   'deactivateUser' against 
   adminPortal#deactivateUser with 
   { userId: rollfiUserId }
6. Log raw Rollfi response at info 
   level, same pattern as existing 
   onboarding calls
7. ONLY on Rollfi success: call 
   store.updateEmployeeStatus(
     employeeId, 'on_leave', 
     { onLeaveReason: reason, 
       onLeaveDate: nowISO, 
       expectedReturnDate })
8. Respond { success: true, 
   status: 'on_leave', 
   rollfiResponse }
9. On Rollfi failure: catch, log error 
   with rollfiErrorBody pattern, 
   respond 500 with details — do NOT 
   touch local store state if the 
   Rollfi call failed (avoid drift 
   between systems)

ROUTE 2: POST /rollfi/employees/terminate
Body: { employeeId: string, 
        terminationReason: string, 
        lastWorkingDay: string }

Logic: same shape as Route 1, except:
- Reject if status already 'terminated' 
  (400)
- Call adminPortal#terminateUser with 
  { userId: rollfiUserId, 
    terminationDate: lastWorkingDay }
- On success: 
  store.updateEmployeeStatus(
    employeeId, 'terminated', 
    { terminatedAt: nowISO, 
      terminationReason, 
      lastWorkingDay, 
      terminatedBy: req.session.userId })
- Same fail-closed rule: do not mutate 
  local state if the Rollfi call throws

ROUTE 3: POST /rollfi/employees/reactivate
Body: { employeeId: string }

Logic:
- Reject with 400 if current status 
  is 'terminated' — message explicitly: 
  "Terminated employees cannot be 
  reactivated. Add them as a new 
  employee if rehired."
- Reject with 400 if current status 
  is already 'active' (nothing to do)
- Call adminPortal#reactivateUser 
  with { userId: rollfiUserId }
- On success: 
  store.updateEmployeeStatus(
    employeeId, 'active', 
    { onLeaveReason: undefined, 
      onLeaveDate: undefined, 
      expectedReturnDate: undefined })
- Same fail-closed error handling 
  pattern

All three routes must return 
consistent error JSON shape matching 
what the rest of rollfi.ts already 
uses (error + details fields), so 
the frontend's existing error-toast 
handling (if any) keeps working 
without changes.
