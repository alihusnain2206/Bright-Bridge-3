## STEP 2 — BUILD

### A. Location management UI (Company Settings)

New "Locations" tab in Company Settings (owner + super_admin), same visual pattern as the
Departments tab:

- List all locations: code, name, address, active status. The auto-created Phase 1
  location appears here like any other — it is EDITABLE (Urban Concepts will rename
  theirs from the company name to "152nd Street").
- Add Location: code (text, e.g. "200"), name, address1/2, city, state, zip. On save:
  1. Insert the locations row
  2. If the company has a Rollfi record: call Rollfi addCompanyLocation (per the docs
     shape from the audit) and store the returned rollfiLocationId on the row. If the
     company has NO Rollfi record (non-payroll company like Urban Concepts): skip Rollfi
     entirely — same if (rollfiCompany) guard pattern as employee sync. No error, no
     warning; just store null rollfiLocationId.
  3. Create the EasyTeam location for the site (per the audit finding) and store
     easyteamLocationId. Run ensureLocationTimezone and ensureTimeOffPolicy for it, same
     as existing locations get.
  4. If Rollfi or EasyTeam creation fails: save the location row anyway with the failed
     ID null, show a clear non-blocking warning with retry (same honest-failure pattern
     as the 8655 upload) — never lose the owner's input, never fake success.
- Edit: code, name, address editable. If address changes and rollfiLocationId exists,
  call updateCompanyLocation (the endpoint we already fixed — companyLocation-wrapped
  payload). Address edit also PATCHes the EasyTeam location.
- Delete/deactivate: soft-deactivate only (isActive=false), and BLOCK if any active
  employee is assigned to it ("Reassign N employees first") — same guard pattern as
  department delete.
- Code uniqueness per company; friendly validation error on duplicates.

### B. Employee location assignment

1. Wizard Step 1: "Location" dropdown next to Department. ONLY render when the company
   has 2+ active locations; with 1 location, silently assign it (no UI change for
   single-site companies). Required when shown. Sets employees.locationId.
2. Employee edit form (Basic Info or Employment tab — match where department lives):
   same conditional dropdown so existing employees can be assigned.
3. Employee profile header/Job tab: display location (code + name) alongside department.
4. Directory: Location column (code + name) + a filter dropdown (only when 2+ locations),
   matching the existing department filter pattern.
5. Rollfi side: when an employee is created at a company WITH payroll and 2+ locations,
   pass their location's rollfiLocationId as companyLocationId in addUser (today it
   passes the company's single location). When an existing employee's location changes
   and they have a rollfiUserId, call updateUser with the new companyLocationId. For
   non-payroll companies / employees with no rollfiUserId: skip, no error (existing
   guard).
6. EasyTeam side: employee registration should use the employee's own location
   (resolveEmployeeLocationId from Phase 1) rather than the company's single location —
   BUT verify this doesn't change behavior for single-location companies (it resolves to
   the same ID). Do not build multi-location JWT arrays yet — that's Phase 3.

### C. Manager assignment with location (assignment only — NO enforcement)

Grant Access flow (Settings → Users & Access): when role "Manager" is selected, show a
"Location" dropdown (required, from the company's active locations). Store it in
user_accounts.locationId. Display the location in the Users & Access list for manager
accounts. UI label for this role in dropdowns/badges: "Manager" is fine (do not invent a
new role value — role stays `manager`).

Explicitly OUT of scope: any change to what managers can see or do. A manager account
created now still sees company-wide data until Phase 3 ships the scoping. Do not add
locationId filtering to any endpoint in this phase.
